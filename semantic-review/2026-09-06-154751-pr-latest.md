# Runtime coordination and provider/catalog planning seams

The remediation adds runtime contracts, a state machine, managed-process/readiness helpers, a local provider adapter, immutable catalog/GGUF/digest utilities, hardware snapshots, fit planning, and additive IPC/WebUI provider paths. Legacy IPC names remain present and the existing model-switch body is retained behind a coordinator mutation lane, while local catalog and fit-plan handlers now exercise the new catalog/planning code. The main limitation is that the coordinator and later cross-boundary integration are still marked incomplete, so several new services remain parallel seams rather than the owners of production chat/readiness behavior. **Watch for:** **confirmed** malformed SSE JSON now terminates the WebUI stream; **confirmed** compatibility tests mostly prove source text rather than runtime alias/lifecycle behavior; **likely** coordinator snapshots can report `idle`/`ready` inconsistently during model switching and process health transitions.

**Verdict**: NEEDS_CHANGES

## High-level view

The legacy aliases are still registered, and `start-server`, `stop-server`, lazy start, and the existing switch implementation delegate through `RuntimeCoordinator`; the coordinator does not yet own all lifecycle/model-load behavior, however. Its readiness executor starts the legacy process but does not invoke the provider adapter or perform a provider/model-specific readiness operation.

Catalog construction, GGUF inspection, streamed digesting, hardware normalization, and fit planning are real implementations. The local catalog IPC path uses inspection and digesting, and fit planning is exposed through IPC, but verification remains deliberately unimplemented until task 8.x and the catalog is not connected to model selection or download verification.

The WebUI now uses `ProviderService` for normal and streaming chat while preserving request parameters, callbacks, and AbortSignal forwarding. The normalized stream path is less tolerant than the legacy parser for malformed events, and the stream reducer/checkpoint/timeout work that would define the intended recovery semantics remains in task 7.x.

The completed-task tests are discoverable in the desktop Vitest glob except for explicitly excluded legacy/custom suites, and several discovered suites execute custom `test`/`describe` wrappers or inspect source strings. They provide useful pure-module coverage but do not prove that Electron IPC handlers, preload aliases, process lifecycle, or model switching work end to end.

### Provider normalization changes the malformed-stream failure mode

`ChatService.handleNormalizedStream` delegates all SSE parsing to `ProviderService.stream` (`webui/src/lib/services/chat.service.ts:395-415`). `normalizeStreamLine` throws `Malformed provider stream event.` when JSON parsing fails or a chunk has no `delta` (`webui/src/lib/services/provider.service.ts:109-123`), and `ProviderService.stream` does not catch that per line before the outer rejection (`webui/src/lib/services/provider.service.ts:82-105`). The old `handleStreamResponse` path caught JSON parse failures and continued reading (`webui/src/lib/services/chat.service.ts:580-620`), so a malformed provider event now invokes the error path and aborts an otherwise recoverable stream. This is **confirmed** and belongs to completed 3.4/3.5 behavior; task 7.1 is the unfinished place to formalize recoverable versus terminal malformed events, but the migration should not regress existing tolerance in the meantime.

The new provider tests cover normal content/reasoning/tool/timing events and cancellation (`desktop/tests/llama-server-provider.test.js:47-89`, `webui/tests/unit/provider.service.test.ts:18-49`), but no WebUI test asserts malformed-event recovery or the terminal/recoverable distinction. This missing coverage is **confirmed**. The desktop adapter silently ignores malformed JSON in its stream parser (`desktop/providers/llama-server-provider.js:207-210`), so the two normalized transports also have inconsistent malformed-event behavior (**confirmed**).

### Coordinator integration preserves aliases but not a complete public lifecycle

The aliases remain registered in `desktop/main.js:3988-4031` and `desktop/main.js:4327-4329`; the existing `performLegacyModelSwitch` still validates the filename, stores the active model, stops/starts the server, waits for the API, reloads the chat window, and emits the existing progress phases (`desktop/main.js:4236-4325`). That preserves the legacy return shape and progress channel, but the coordinator only wraps the operation in `EnsureReadyRegistry.runMutation` (`desktop/runtime/runtime-coordinator.js:102-114`). It does not transition the state machine to `stopping`, `starting`, or `ready` for that operation. If the server was not running, the switch callback returns success without starting it and the coordinator remains `idle`; if it was running, the callback performs the stop/start while the public coordinator state remains whatever it was before the mutation. This is **likely** to make `get-runtime-snapshot` disagree with `get-server-status` and the switch progress events.

Similarly, `RuntimeCoordinator.start` transitions to `ready` after the injected legacy `start` function resolves (`desktop/runtime/runtime-coordinator.js:57-78`), but the legacy function only spawns/configures the process; the actual health wait is performed separately by callers such as `transitionToMainApp` and lazy start. That makes the normalized `ready` state mean “spawn returned” rather than “server is healthy and model-ready.” The coordinator itself also never calls `ProviderRegistry.invoke` or `LlamaServerProvider.ensureReady` (`desktop/runtime/runtime-coordinator.js:116-132`), so provider/model readiness is not yet the source of truth. These are **likely** bounded gaps in unfinished 2.4/2.5 and 11.1/11.2, not evidence that the legacy aliases were removed.

### Catalog, digest, and fit seams are implemented but only partially connected

`buildLocalCatalogRecords` invokes bounded GGUF inspection and streamed SHA-256 digesting for installed files (`desktop/main.js:3940-3971`), and `get-model-catalog` merges those records through the coordinator (`desktop/main.js:3993-3995`). `get-model-fit-plan` validates a basename and evaluates a pure plan against supplied or detected hardware (`desktop/main.js:3996-4001`). The catalog merger retains stale records and forces unverified artifacts unavailable (`desktop/catalog/model-catalog.js:52-63,124-158`), while the identity helper only treats verified digests as executable (`desktop/catalog/model-identity.js:44-60`).

However, the local records explicitly set `verification: 'unverified'` and then force `record.digest.verified = false` (`desktop/main.js:3944-3969`). No artifact verifier or trusted digest source is connected, so every locally catalogued model remains unavailable for execution under the new catalog semantics. That is **confirmed**, but it is the intentional unfinished 8.1 verification boundary rather than a defect in completed 4.x. The catalog IPC also re-reads and re-digests every installed model on each request; the digest is not cached and the `includeDigest` option does not change `buildLocalCatalogRecords` behavior. The performance/resource qualification is **likely** and belongs to unfinished 11.3/8.1 unless the catalog is only called infrequently.

The fit planner is pure and deterministic (`desktop/planning/fit-plan.js:100-180`), and the completed property test checks repeatability, non-mutation, incomplete-input conservatism, and 100 runs (`desktop/tests/properties/fit-plan.property.test.js:28-61`). It is advisory only: later unfinished 10.3/11.1 work still needs to consume availability and fit status in model selection rather than leaving the result as an isolated IPC response.

### Compatibility coverage is discoverable in part, but not a boundary test

The included runtime compatibility suite checks that strings for IPC channels and legacy behavior markers remain in `main.js`/`preload.js`, then exercises only independent controlled fixtures (`desktop/tests/compatibility/runtime-compatibility.test.js:23-92`). The inventory suite makes similar source assertions (`desktop/tests/compatibility-inventory.test.js:16-52`) but is explicitly excluded from `desktop/vitest.config.js:7-17`; the custom state-machine and catalog/property suites also use ad-hoc runners rather than Vitest assertions (`desktop/tests/runtime-state-machine.test.js:10-14`, `desktop/tests/properties/catalog-identity.property.test.js:43-54`). This is **confirmed** test-quality risk: a missing handler body, a mismatched IPC return value, an unstarted process, or a broken switch cleanup path can pass these tests while the source token remains present. The gap is part of unfinished 11.2/11.4, although completed 1.4 should be strengthened before claiming compatibility is protected.

The pure contract coverage is useful; the missing boundary coverage is **confirmed**: no test invokes `ipcMain.handle` through a mocked Electron boundary, verifies preload callback cleanup, or exercises lifecycle health failure and model-switch stop/start/recovery outcomes.
