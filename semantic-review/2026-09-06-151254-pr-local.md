# Runtime contracts, provider normalization, catalog, and fit-planning foundation

The change adds contracts and mostly pure services for lifecycle coordination, provider normalization, model identity/catalog merging, GGUF inspection, hardware snapshots, and conservative fit planning. It also adds fixtures, Vitest configuration, compatibility inventory checks, and example/property tests, while preserving legacy IPC and chat paths in places. The central gap is that the new runtime/provider/catalog services are not wired through a coordinator or existing lifecycle/model-management handlers, so the completed-task claims describe available building blocks rather than active end-to-end behavior. The WebUI provider migration also does not provide the required safe stream failure and cancellation semantics.

Watch for: **confirmed** — the new `EnsureReadyRegistry`, `ManagedProcess`, `ProviderRegistry`, `LlamaServerProvider`, and `ModelCatalog` have no runtime-coordinator integration in the changed `main.js`, so lifecycle and model switching still use legacy mutable state; **confirmed** — the WebUI normalized stream path silently drops or throws on malformed events and does not cancel a blocked reader; **confirmed** — the normal desktop Vitest configuration excludes the compatibility inventory and several completed baseline/contract tests.

**Verdict**: NEEDS_CHANGES

## High-level view

**confirmed** — the implementation establishes useful serializable vocabulary and pure domain logic, and the catalog, GGUF inspector, digest identity, hardware normalization, and fit planner have meaningful behavior rather than empty stubs. Their outputs are not yet the application source of truth: `main.js` only exposes additive hardware-snapshot handlers, while startup, model switching, provider calls, and process ownership remain on old paths.

**confirmed** — the provider boundary is split between a tested main-process llama-server adapter and a renderer `ProviderService` that still performs direct HTTP transport. The renderer path does not consume the main adapter’s normalized envelopes or stream contract, and its failure/cancellation behavior falls short of the stated contract.

**confirmed** — the test foundation covers representative pure cases and 100-run catalog/fit properties, but the compatibility inventory mostly checks source text and fixture metadata rather than executing existing startup, router, IndexedDB, streaming, and preload behaviors. Test discovery also excludes some files that the completed tasks rely on, so green results would not establish the claimed baseline.

### Runtime lifecycle, process ownership, and readiness remain isolated from the application

**confirmed** — `runtime-state-machine.js` provides the explicit adjacency table, structured transition reasons, bounded history, invalid-transition diagnostics, and epoch rejection. `managed-process.js` validates a curated executable, rejects renderer launch arguments, captures bounded output, uses ownership tokens, polls health, and classifies exits. `ensure-ready-registry.js` coalesces by provider/model key and serializes its queue. These modules are substantive, but they are not connected to the application.

**confirmed** — the only new runtime import in `main.js` is `detectHardwareSnapshot` (around `main.js:11`), and the only new handlers are `get-hardware-snapshot` and `refresh-hardware-snapshot` (around `main.js:3950-3958`). There is no `RuntimeCoordinator`, no import of `RuntimeStateMachine`, `ManagedProcess`, or `EnsureReadyRegistry`, and no provider/catalog registry installed into the existing `start-server`, `stop-server`, `switch-model`, or chat paths. Legacy globals and functions therefore remain the owners of lifecycle/model state. Task 2.4 is still marked `[~]`, but tasks 2.1–2.3 are marked complete with an intent that depends on those seams; classify them as **partially implemented** until an integration layer exercises them.

**likely** — `EnsureReadyRegistry` can attach a new caller to an operation that has already lost its last caller and had its shared controller aborted: `_detachCaller` aborts when the caller count reaches zero, but the operation remains in `_operations` until execution settles, and a subsequent `ensureReady` joins that aborted record. A new caller should either revive safely or force a fresh operation; add a regression test for “last caller cancels, then a new caller joins” and define the expected epoch/result semantics.

### Provider normalization is implemented in main-process code but not authoritative for chat

**confirmed** — `provider-contract.js`, `normalize.js`, `llama-server-provider.js`, and `provider-registry.js` expose descriptor, capability, readiness, health, chat, stream, cancellation, status, and redacted error shapes. The main adapter preserves request bodies, local defaults, reasoning/tool events, model/health/slot endpoints, and AbortSignal propagation in its direct tests. This supports a substantial portion of tasks 3.1–3.3.

**confirmed** — the renderer migration in `chat.service.ts` delegates to `webui/src/lib/services/provider.service.ts`, but that service still calls `fetch('./v1/chat/completions')` directly and constructs its own response/event types. It never invokes the main-process `ProviderRegistry` or `LlamaServerProvider`, and `complete()` returns only model/content/reasoning/tool calls, dropping normalized timings and prompt progress. HTTP errors are thrown as raw `Error` objects, not `ResultEnvelope`/`RedactedError` values. Task 3.4 preserves much of the callback surface but does not consume the common provider contract as specified.

**confirmed** — malformed stream handling is unsafe in the new renderer path. `ProviderService.normalizeStreamLine()` calls `JSON.parse()` without recoverable/terminal classification; `ProviderService.stream()` does not catch parsing errors to emit a protocol diagnostic, and the caller converts the failure to a generic stream error. In the main adapter, `llama-server-provider.js` catches JSON parse failures in `parseData()` and simply returns, so malformed events are silently discarded without the required diagnostic. Neither path implements heartbeat timeout or persists partial output, although those are part of the claimed stream/provider behavior.

**confirmed** — cancellation is not bounded for a blocked response reader. Both provider stream implementations check `signal.aborted` before/around reads, but neither calls `reader.cancel()` or races a pending `reader.read()` against the signal. If the body never resolves another read, cancellation cannot be observed within the two-second target. The tests cover an already-aborted non-stream request, not a controlled reader blocked during streaming. This is a blocking gap for task 3.2’s cancellation claim.

### Catalog identity and GGUF inspection are useful pure components, but no catalog integration exists

**confirmed** — `model-catalog.js` creates frozen snapshots, merges local/curated/router/discovery observations, retains source failures/stale records, deduplicates verified digests while retaining aliases, sorts deterministically, and round-trips JSON snapshots. `model-identity.js` streams digest input and prevents unverified records from being execution-available. `gguf-inspector.js` bounds bytes, keys, strings, arrays, extensions, and metadata, reports known/unknown/malformed fields, and does not load a model. The example tests and 100-run properties exercise these pure behaviors meaningfully.

**confirmed** — no existing model scan, curated-download, router, or model-switch handler imports `ModelCatalog`, `gguf-inspector`, or `model-identity`; `main.js` has no catalog service setup. Thus tasks 4.1–4.3 are standalone modules, but user-visible model catalog and execution gating do not consume them. The requirement that an unverified artifact cannot be executed is enforced by `executionAvailability()` only; it is not enforced at the current download/model-switch integration seam.

**likely** — catalog source failure and refresh behavior is tested only through synthetic source objects. There is no controlled fixture connecting an actual local GGUF scan, curated manifest, router response, or download digest to the merge path, so alias retention and stale-source behavior could diverge when real adapters supply their current record shapes. Add adapter-level fixtures and an integration test that drives existing model handlers through the normalized catalog.

### Hardware snapshot and fit planning are the best-integrated completed slice, with scope limits

**confirmed** — `hardware-snapshot.js` is imported by `main.js` and exposed through additive IPC handlers while legacy hardware handlers remain unchanged. Probe failures become missing values, confidence is conservative, legacy backend flags are retained, and tests cover complete, partial, and failed probes.

**confirmed** — `fit-plan.js` is pure and deterministic, uses a safety fraction, overhead margin, KV estimates, conservative unknown status, offload capability checks, and deterministic alternatives. Example and 100-run property tests cover these behaviors. It is not called by the renderer/model-selection path, so the “warn before user-initiated load” behavior is not present; tasks 5.1–5.4 are complete as a planning API, not as an end-to-end feature.

### Compatibility and test harness do not demonstrate the claimed completed baseline

**confirmed** — `desktop/tests/compatibility-inventory.test.js` verifies that listed IPC channels and source names appear in files, checks a few legacy adapter defaults, and asserts that one unknown channel is absent. The WebUI inventory test similarly checks that paths exist, that Dexie version/index strings are present, and that fixture metadata contains expected labels. These checks do not execute server startup/stop, curated selection/download, router loading, IndexedDB retrieval, stream cancellation, or preload authorization. Task 1.2 and optional task 1.4 are therefore **fixture/inventory scaffolding**, not behavioral compatibility coverage.

**confirmed** — `desktop/vitest.config.js` explicitly excludes `tests/compatibility-inventory.test.js`, `tests/runtime-contract.test.js`, and `tests/helpers/**/*.test.js`. The completed baseline inventory and parse-print-parse helper tests consequently are not part of the default desktop `vitest run`, while the WebUI unit configuration includes its compatibility directory but has no test exercising changed `ChatService` behavior. This makes task 1.3’s “shared runnable harness” and task 1.4’s regression protection incomplete.

**confirmed** — the 100-run fast-check tests are present for catalog identity/failure tolerance and fit planning, with the required Feature/Property comments. They validate pure module invariants, but do not compensate for missing lifecycle/provider integration or compatibility behavior. The runtime/provider completed tasks have example tests, not a cross-boundary test proving that the new modules are invoked by the application.

**likely** — the known WebUI type-check blocker remains unresolved by inspection of the migration: `ProviderService` introduces a second normalized event/response model while `ChatService` continues to carry the old direct-stream implementation and broad API types, and the new service assumes `choice.message.content` is assignable to `string` and parsed stream chunks always have the expected shape. The diff provides no type-check result or compatibility type adapter, so rerun the check after consolidating the service contract; do not mark the WebUI portion complete based on source compilation assumptions.
